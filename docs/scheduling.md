# How dibs decides, and what it promises

The README covers using dibs. This is the detail: who goes next, what a lease guarantees, and the knobs that pause, pace and reset work.

## How a turn is decided

A waiter starts when all of these hold:

1. **Each resource it names has a free slot**, or the machine has room for one more on top (see "Running side by side" below).
2. **Nobody ahead of it in line wants the same resource and could use it.** Your own session's hold on a resource covers your runs on it, and so does the `dibs run` you're nested in. "Ahead" means arrival time, shifted by: its run time (what its command has taken, the median of its last ten runs, or `--est` until dibs has seen it, or 2 minutes for one never seen: shorter than 2 minutes moves it up, longer moves it back by the difference, an hour at most, so a 30-second check goes ahead of a 20-minute suite that arrived up to about 19 minutes before it, and no job waits behind quicker work much longer than it runs), heavy use of the same resources by the same agent in the last hour (5 minutes of use costs a minute, up to 10 minutes back, for fair share: an hour of test runs doesn't cost you your turn on the simulator), and priority (`urgent` +2 hours, `high` +1 hour, `normal` 0, `low` -10 minutes, `idle` -60: a high job goes ahead of a normal one unless that has waited an hour longer. `low` and `idle` run at background priority, and `idle` starts only when nobody else is waiting) and by a deadline that's getting close (`--by`: once slack drops under 20 minutes, you move up, by at most an hour). Every shift is bounded, so nobody waits forever. **The quick lane:** a command that takes under `quickUnder` (15 seconds unless set; the middle of its last ten runs, or `--quick` or an `--est` that short before dibs has seen it) starts at once: past the line, the slots of shared and pool resources, warning memory pressure, swap and the load ceiling. The disk floor, critical pressure, file leases and someone else's hold still stop it, and it never pauses anyone. At most 2 run at once. On an exclusive resource it goes to the front of the line instead of alongside, unless the resource says `quickAlongside: "other-repo"` (deploys do) and every job on it is another repo's. A run that goes over `quickUnder` loses the pass for its command until a run comes in under again. The board marks these `quick`. **Pairs that slow each other:** dibs compares each command's runs that spent most of their time beside a kind of work (a resource) with its runs that didn't. If it has taken 1.8 times as long or more beside work running now (three runs of each to go on), or makes that job take that long, it waits for that job to finish, but never longer than its own usual run time since it joined (`blocked by together`). **Backfill:** you may pass someone who can't start yet anyway, if you'll be done before they could have started.
3. **It fits the budgets.** What jobs book never adds up past the memory budget (8 GB by default), whatever the machine looks like: nothing starts past it. Memory counts what each job was handed (asked for, or raised to what its command has used), or what its whole process tree was last measured using when that's more: a job that outgrows its number still fills the machine. **Booked at what it uses:** a run measured for 3 minutes books its peak so far plus 1 GB instead of its ask, never more than its ask. Once its memory has stopped climbing for 2 minutes, it books what it uses now plus 1 GB, or only what it uses once it has been idle 5 minutes. The gap between asks and use goes to waiters, but a waiter let into it (one that wouldn't fit if every running job used its full ask) also needs the machine to show the room: memory pressure normal, swap not growing, and the job plus 3 GB (or a fifth of the machine's memory, if that's more) free by the OS's reading (`kern.memorystatus_level` on macOS, MemAvailable on Linux). So a job that spikes later can't push the machine into swap. Each measured run records how far in it reached its peak, and a running job that has gone well past where its command's last 5 runs peaked (a quarter longer, plus 2 minutes, not counting time paused) is done growing: it counts at what it books, not its ask, so a waiter beside it needs only that much of the budget. A command that peaks late, or whose runs don't say when they peak, keeps its ask until then. Past the booking too: when what running jobs measure using right now, plus the job, fits the budget and the machine shows that same room, it starts; bookings keep a job's peak for minutes after it falls. Swap that's high but holding still doesn't count against that room; only growing swap and memory pressure do. Cores count what each running job was last measured using (every 10 seconds), and what it asked for until its first measurement: suites and builds ask for their peak and spend most of a run under it, and a few too many busy cores only slows everyone a little, so on a quiet machine the CPU budget steps aside. A job as big as the whole budget runs when nothing else is; your own holds and file leases don't count as something else. A run inside your own hold (or nested in your `dibs run`) uses the memory that hold reserved, so the two count once: at the larger of what the hold reserved and what the runs inside it use. Paused jobs keep their memory but take no cores.
4. **The machine can take it.** Free disk covers the job's need and stays above `minDisk` (5G): below that nothing starts, `urgent` work included (runs inside your own hold go on what the hold got). Low disk is a wait, never a refusal at the start: the job keeps its place, free disk is read again at every poll, and it starts the moment there's room. Only a job that writes next to nothing starts below the floor, keeping 1 GB free: one whose last ten runs (at least two, none run while the watcher cleared caches) ate under 100 MB at the middle, and whose last run did too, on any resource; before that, only one whose `--disk` says so (under 100 MB, or 1 GB or less on resources that declare no disk need: tests, deploys, locks). A job the person waits on (`high`, `urgent`, or `--by` with `-m`) may go down to 3 GB free, the same hard floor the watcher pauses jobs at, and doesn't wait for the room kept for swap. Under 1 GB free the watcher pauses the dibs job writing the most, whatever its priority or resource, one each pass, says so to its session and the person, and resumes it at 2 GB. The machine isn't short on memory right now: while the OS reports memory pressure at warning or critical, or swap is over `maxSwap` (4G), grew by more than 512 MB in the last 5 minutes and is still growing over the last minute and a half, work below `urgent` waits while anything else is running. The OS's free-memory reading counts compressed and cached memory as free and can say 60% while the Mac pages gigabytes to disk, and on macOS swap grows on the startup disk. Swap alone doesn't count: macOS keeps it allocated for hours after a crunch ends. dibs keeps a swap reading every 30 seconds in `~/.dibs/swap.json` to see the growth. With nothing else running, one job starts, since waiting can't help then. `"maxSwap": null` turns the swap check off; memory pressure still counts. Swap needs free disk to grow into, so while swap is growing or memory pressure is above normal, work below `urgent` also keeps `swapRoom` (3G) free on top of what it needs (8 GB with the stock `minDisk`), and while free disk falls more than 3 GB in 5 minutes, fast enough to be under that within 10 minutes, it waits for it to hold steady (a disk with plenty free that two builds are writing to holds nobody up); in both cases one job still starts with nothing else running. If the swap, pressure and disk-for-swap waits keep every job out for 10 minutes, counting only starts that went through them (not runs inside your own hold, not urgent work), the smallest and shortest waiter they hold back starts anyway, one at a time until its memory has held steady for 2 minutes, while free disk is over `minDisk` and pressure isn't critical. `"swapRoom": null` turns the room off, and `"minDisk": null` the floor. For jobs of 2 GB or more, the OS also reports at least 15% of memory free. If free disk can't be read, the board says `disk unknown` and `dibs run` says the disk check is off.
5. **The load is under the ceiling**, when there is one (`maxLoad`, set by `dibs pace`). `urgent` and `high` work skips this rule, and so does work that already holds a lease (below).
6. **The last user's `onRelease` has finished** putting the resource back.
7. **A quota has the tokens**, for `quota:<name>` (below).

File leases (`files:<path>`) skip rules 3 to 5: holding a path runs nothing. See [files.md](files.md).

**Bigger than the machine.** A job that asks for more memory or cores than the budgets hand out at once (`--mem 12G` with an 8G budget, `--cpu 9` with 6 cores) could never start, so `dibs run` and `dibs hold` refuse it at once with exit 2 and the most it can ask for here. Only a number you typed does that: a size dibs chose (the resource's default, or one learned from runs on a bigger machine) is booked at the most this machine hands out, and the job runs. In a group of machines it also names the ones it would fit (`--on <machine>`, or `--anywhere`). A waiter that stops fitting while it waits (the budget was lowered) leaves the line the same way, and its agent hears why through the hook. 

**Waiting long on the budget.** A waiter held back by the memory or CPU budget for more than `starveAfter` (3 minutes) goes ahead of lighter jobs that would otherwise keep passing it, but only of those that would delay it: dibs works out when enough of what's booked will really end for it to fit (a job already past its usual time counts as running as long again, not as ending in 30 seconds), and a job that will be done before then still starts. A waiter that needs three quarters of the budget or more reserves it only once it could start within 5 minutes; further off, it waits for a quiet moment and other jobs start meanwhile. High and urgent work never waits behind a lower-priority job's reservation. A job that usually uses more than the whole budget goes to an on-demand machine at once when one can take it (docs/machines.md). A job whose run time dibs knows (`--est`, or history) starts past a waiter reserving memory when that waiter's own start rests on a job of unknown length (no `--est`, no history, a hold, or one past its time), as long as it fits now: that start is only a guess.

Run times come from history (the median of the last 10 runs of the same command on the same resources), or `--est`, or a 5-minute guess. The same command means the same program and its first three words that aren't flags, each cut to its last path part (`npm run lint`, `node run.mjs` from any folder). For `xcodebuild` it's the first such word, the scheme, the configuration and the action, so a 20-second incremental build and a 7-minute archive of one project learn apart. History written by 0.0.74 and earlier kept only the first word; it counts for a command until the command has history of its own.

## What it guarantees

- **A lease belongs to a process, not a clock.** `dibs <res> -- cmd` holds until `cmd` exits, however long that takes. No keepalives, and no expiry stealing a live run.
- **Crashes clean up.** The command runs in its own process group, and children that split off into their own group (browsers, dev servers) are noted every 3 seconds while it runs. When it exits, or dibs is killed, all of them are killed and the slot frees. After a `kill -9`, a small watcher each run leaves behind does it within a second or two; a group that split off in the last 3 seconds before the kill is left to the next dibs call that reads the state. A group whose number was reused by another program is left alone. If the process table can't be read (spawn failures under memory pressure), nothing is reaped until it can. Pids are checked against their start time, so a recycled pid can't pose as a live holder.
- **Signals pass through.** Ctrl-C or SIGTERM to dibs reaches the command.
- **Holds end on their own.** `dibs hold` belongs to the Claude session that took it, and ends when that session dies, at `--for` (max 1 hour), or on `dibs release`.
- **Waiting is never blind.** The board says in a sentence what each line is doing and who's next (`Simulator: onboarding is using it, about 4 min left. Next: ios-checkout.`), and `dibs why` says where you are, when you start and what you're waiting for. A start time is "about N min" only when every job in the way has a run time from history or `--est`; otherwise it's "as soon as X finishes", or unknown when the wait is on the machine (disk, memory, load). `dibs --detail` rows say which rule stops each waiter (`[blocked by slot: xcode-build]`, `[blocked by files: src/auth/**]`, `[blocked by disk: 8.8G free, needs 10G]`, `[behind web-app]`). While you wait, dibs says once where you are, when you start, what you're waiting for, who to message to go first and when the wait gives up; after that, one line when your place or the reason changes, and otherwise every 2 minutes. When it gives up (exit 75) it prints the exact command that keeps your place.
- **Waiting ends when your turn comes, not at a deadline you didn't pick.** Inside Claude Code, `dibs run` and `dibs hold` wait as long as it takes: Claude Code doesn't kill a Bash command at its timeout, it moves it to the background and tells the agent when it exits, output and all. So don't run it again after the move; a second copy would run the command twice. dibs knows it's there from `CLAUDE_CODE_CHILD_SESSION=1`, which Claude Code sets only in its own tool calls, and goes back to a limit when background tasks are off (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, or bare mode via `CLAUDE_CODE_SIMPLE=1`). Everywhere else (Codex, scripts, a terminal) dibs gives up at `--max-wait` (8m), which fits a 10-minute tool call. `--wait` lifts the limit anywhere; put it in a background shell if your tool call has a time limit of its own.
- **Exit 75 is not a failure.** It means your command never started because dibs stopped waiting in line. Your place is kept for 2 minutes: the exact same command again (same session, resources and command; flags may differ) picks it up where it was.
- **`--notify <file>` says when it's over.** When dibs exits, for any reason, it appends one JSON line to the file: `{"at", "code", "started", "res", "cmd", "cwd", "secs", "pid"}`. `started` is false when the command never ran (exit 75, exit 74 before launch, a bad simulator), true once dibs had recorded it and started it, and null for a job sent to another machine. Give each job its own file and wait for it to fill (`until [ -s build.done ]; do sleep 5; done`, or a Monitor tool) instead of polling the board. A `kill -9` writes nothing. Inside Claude Code you rarely need it: a background Bash call already wakes the agent when it ends.
- **Random ports.** `--port NAME` puts a free port in `$NAME`, so two Playwright runs never fight over 4173.
- **Nesting works.** A script running under `dibs run sim` that calls `dibs run sim` itself goes straight ahead instead of queueing behind its own lease. One that needs more than its lease has (`dibs run deploy -- ./ship.sh`, which runs `dibs run xcode-build`) waits only for the rest, and goes ahead of waiters that hold nothing (10 minutes, less than `high`'s hour): it passes the load ceiling, but never jumps `high` or `urgent` work or pauses anyone's job. The board shows `[holds deploy, goes first]`. A session's own `dibs hold` counts the same way for its first 10 minutes. A lease on a resource that isn't configured, a run at `low` or `idle`, or a wait asked for with `-p low` doesn't count. `DIBS_LEASE` counts only when that lease's process is really an ancestor of the caller.
- **Something always runs.** dibs never leaves every job paused. Each pause it makes on its own (for urgent work, memory pressure or low disk) is refused if it would leave no job running, counting a run nested in a paused one as paused too. If every running job is paused anyway, because the one still going ended, the next dibs call that changes the state (and the watcher every 10 seconds) resumes the paused job closest to done, and `~/.dibs/cool.log` says so. dibs also never pauses a job about to finish: under 2 minutes left, or in the last tenth of its usual run. With nothing running at all, a small job (2 GB or less) that's urgent or known to take under 2 minutes may start past memory the paused jobs and idle holds still book, unless memory pressure is critical. Only the person's own `dibs pause` may leave every job paused. A job dibs stops and requeues for the disk (below) isn't paused: it gives back all its memory, so stopping it may leave nothing running, and that's meant.
- **Agents know each other by name.** dibs reads the Claude session name from `~/.claude/sessions`, the same name `SendMessage` uses.

Exit codes: the command's own, or 75 gave up waiting in line (not a failure: the command never started), 1 nothing matched (`mine`, `release`), 74 not enough disk (the run needs more than the whole disk, or the wait limit ran out while disk held it; low disk is otherwise a wait), 76 lost the coordinator or the other machine before a remote job started (safe to send again), 77 lost it after the job started (it may have run: check first), 127 the command didn't start, 2 bad usage (including a resource name close to a real one, an agent's high or urgent `dibs boost` without `-m`, and a `dibs run` you already have waiting or running), 70 dibs itself crashed (a bug in dibs; report it with `dibs ask`).

## Measuring what jobs use

`--mem` and `--cpu` (or the resource's defaults) are guesses, and macOS can't cap a process tree without root. So instead of a cage, dibs keeps the numbers honest. While anything runs, one `dibs run` every 10 seconds measures every running lease: physical footprint and CPU over all its process groups, plus a pool simulator's own processes, which run outside the job. A run nested in another is counted once, as itself. The peak goes into history with the run time, and the next run of the same command is planned at the most any of its last 5 measured runs used, when that's more than it asked for. Failed and killed runs count. A command never measured goes by its family: the same resources, program and next word, so `npx playwright test b.spec.ts` learns from `a.spec.ts`, while `npm run lint` learns nothing from `npm run build`. `dibs run` and `dibs when` say so (`xcodebuild build used up to 6.1 GB of memory (it asks for 4.0 GB) in recent runs, so dibs plans for that.`). A command that has used more than the whole memory budget is planned at the budget instead, so it starts once the budget is empty rather than once the machine has no leases at all. `dibs run` says it (`usually uses up to 14 GB of memory, more than the 11 GB dibs shares out at once, so dibs plans it at all 11 GB: it starts when no other job is using that memory.`), the plain board says the waiter is waiting for `all the memory dibs shares out to be free`, and `dibs --detail` marks it `[usually uses ~14G; planned at the 11G budget]`. History is kept per command shape (the program and up to three bare words; xcodebuild by scheme, configuration and action), so a build and a test of one project learn apart.

The board flags a running job past what it was handed by more than 10%: `[over: using 6.0G of 4.0G]`. Under memory pressure, the job furthest over is paused first (see below). Ask for what you need with `--mem` and `--cpu`.

**Linux.** With `"enforce": true` in config.json, each job runs in a `systemd-run --user --scope` with `MemoryHigh` and `CPUQuota` at its numbers: it's throttled past them, never killed. Where systemd user sessions don't work (containers, WSL1), jobs run as before.

**A capped scratch volume (macOS).** `dibs setup scratch [--size 40G]` prints the admin commands that make an APFS volume with a quota for build output, so a runaway build fills its own space instead of the disk every agent shares. dibs runs none of them. `dibs setup scratch --check` says how full it is.

## Rate-limit quotas

`quota:<name>` shares an API's rate limit between scripts, so they wait their turn instead of getting 429s:

```json
"quotas": { "asc": { "per": "1h", "limit": 300 } }
```

```bash
dibs run quota:asc --cost 3 -- ./upload-screenshots.sh   # takes 3 tokens when it starts
```

A bucket holds at most `limit` tokens and refills `limit` every `per`, smoothly. A job waits until its bucket has `--cost` tokens (default 1), after anyone ahead of it for the same bucket, so a big request isn't passed forever by small ones. Tokens come back with time, not when a job ends. A quota costs no slots, memory or cores; combine it with a resource (`dibs run quota:asc,deploy -- ...`) when the work needs one. The board lists every bucket and what's left in it.

## Profiles

A project whose suite always needs the same resource, ports and sizes can name them once in `~/.dibs/config.json` instead of a wrapper script:

```json
"profiles": { "playwright:web": { "res": "playwright", "ports": ["WEB", "API"], "mem": "3G", "cpu": 2 } }
```

```bash
dibs run playwright:web -m "e2e" -- npm run e2e   # playwright, $WEB and $API set, planned at 3G and 2 cores
```

A profile sets `res` (one name, a comma list or an array), `ports`, `mem`, `cpu`, `disk` and `est`. Flags on the command line win over it. `dibs when` and `dibs hold` take profiles too. A profile's name can't be a resource's or start with `files:` or `quota:`, and a bad one fails every call with its key named.

## Overrides, by the person or any agent

Anyone may `dibs boost`, `pause`, `resume`, `stop` and `cap` any job: the person, or any agent, its own session's work or another's. Each change is kept on the job with who made it (`owner.by`, the pause's `by`, `stopBy`; none means the person), shown on the board (`[boosted by web-app: release blocked]`, `[paused by web-app]`) and logged in `dibs history` as an `override` event with `by` and `byAgent`.

- An agent raising a job to `high` or `urgent` passes `-m`, as it does on `dibs run -p`, so everyone sees why.
- An agent's urgent gets what the person's does: past the swap and disk-room waits (only urgent work starts during those), past paused jobs' booked memory, and pausing low runs for a slot. The hard limits hold for everyone: below `minDisk` nothing starts but jobs that write next to nothing, the memory budget holds unless the machine really has room, critical memory pressure stops the small-job exceptions, and dibs never pauses every job on its own.
- A job that was stopped tells its agent who stopped it and to find out why before running it again.

## Pausing low-priority work

- **For urgent work.** When an `urgent` or `high` waiter is stuck behind a `low` or `idle` run on a full resource, dibs stops that run's whole process tree (SIGSTOP on every process group it has) and lends the waiter its slot. It pauses only as many runs as it takes, and only if that lets the waiter start right away; if something else would still block it (normal work holding another resource it wants, the memory budget, disk), nothing is paused. The paused run resumes (SIGCONT) the moment the waiter's lease ends, whether it finished, crashed, or was killed: whatever dibs call next reads the state does it.
- **Under memory pressure.** `dibs throttle --watch` reads the OS memory pressure every 10 seconds (`kern.memorystatus_vm_pressure_level` on macOS, `/proc/pressure/memory` on Linux). After two critical readings in a row it pauses one idle or low run (the one furthest over the memory it was handed first, then idle before low, then the most memory), and another after each further two. After a minute of normal readings it resumes one, lighter first, then waits another minute before the next. A warning reading resets both counts, so nothing flaps while the machine hovers. When the watcher stops, it resumes everything it paused; if it dies, the next dibs call does.
- **When swap fills the disk.** Holding new starts doesn't stop jobs already running from growing. The same watcher reads free disk every 10 seconds: while it's under `minDisk` (never under 3 GB, whatever `minDisk` says) and swap is still growing (or free disk fell more than 3 GB in 5 minutes), and still is over the last minute and a half, it pauses one more run each pass, two when free disk is falling fast enough to be down to 1 GB within two minutes: a job on top first, then `idle`, `low` and `normal` work, newest first. `urgent` and `high` work and holds are never paused, and nothing is killed. Once free disk has been back over the line it pauses at and steady for a minute, it resumes one, then another a minute later. A paused job's memory stays in swap, so the disk may never come back over the line: after 3 minutes with nothing growing or falling it resumes one anyway, since waiting frees nothing then. Free some space or end a paused job yourself if it keeps happening.
- **Before the disk runs out.** Under twice `minDisk`, the watcher clears caches that rebuild themselves (npm's and Homebrew's, simulators `simctl` calls unavailable, Xcode DerivedData no build has touched in a day), at most every 30 minutes and again when the disk drops under the floor, and logs what it freed in `~/.dibs/cool.log`. Then each session with something of its own to free (a scratch folder over 2 GB, or running jobs that wrote a gigabyte or more) hears through the hook how much is free, what's growing fastest, whose folder holds the most, what dibs freed, and to free its own build output and scratch. It hears once per band: once under twice the floor and once more under the floor, and again only after the disk has had room (over twice the floor) and falls again. Other sessions hear nothing; the person sees the whole machine in `dibs alerts`. If the throttle watcher isn't running, the coordinator (`dibs serve`) sends the notes and clears the caches instead. Under the floor the note says to save work now, and names each agent's running jobs (they may fail writing) and waiting ones. A job paused for the disk tells its agent through the hook right away.
- **Who is filling the disk.** While free disk is under `minDisk`, or a waiter is held for its own disk need, the same watcher measures the session folders in Claude Code's temp folder (`/private/tmp/claude-<uid>/<project>/<session>`) every 10 minutes and keeps the three biggest over 2 GB in `~/.dibs/hogs.json`. Each one's agent (the one that made its biggest scratchpad folder, else the session's main thread) hears once per drop, through the hook, how big it is, what fills it (git worktrees, node_modules) and how to free it. A disk wait (`dibs why`, `dibs when`, the wait message) names the biggest folder and whose session it is, so a waiting agent knows whom to ask: only that session, or the person, may delete there. It also names what grew most since the last reading, 10 minutes before (each session folder, swap, simulators, Xcode build output, caches, and dibs's copies of other machines' jobs, read from twice the floor down): `Growing fastest: swap, up 2.5 GB in 10 min`. Under half a gigabyte isn't named. Memory pressure easing doesn't resume what the disk paused. If the watcher stops while the disk is still short, its disk pauses stay for a minute so the restarted watcher takes them over, instead of every paused job resuming at once.
- **Never all of them.** None of these pauses the last running job, or one about to finish (see What it guarantees).
- **When the paused jobs themselves fill the disk.** A paused job keeps its memory, and under memory pressure that memory goes to swap, which fills the disk the job is waiting for. So while free disk is under the line and swap is still growing, the watcher stops one disk-paused job each pass, the one using the most memory, instead of pausing another. The job isn't lost: its own `dibs run` puts it back at the front of its line and runs the command again from the start once there's room, in the same call, and its agent hears why through the hook. Only on resources marked `rerun` (test, playwright, xcode-build and heavy by default; never deploy or sim), never a job a person or agent paused, and never one about to finish. The same goes for a job running far past what it booked, paused or not, even the only one running: at least 4 GB over its booking and either twice it or more than all the memory dibs shares out. That job goes back at the front booked at what it really used (up to the budget), what it used goes into the history so later runs are planned at it too, and it starts again only once that much memory is really free and swap holds still. A job stopped this way once isn't stopped for it again.
- **What stays the same.** A paused run keeps its lease and its place. Its clock stops, so time-left estimates and run-time history skip the pause. Its owner sees `paused your job for ...` and `resumed your job after ...` on stderr, and the board says why (`paused so web-app's urgent deploy could go first`; `dibs --detail`: `[paused for <who>]`, `[paused: memory pressure]` or `[paused: disk low]`). High and urgent work is never paused, and neither are holds; normal work only for the disk.
- **Memory.** A stopped process keeps its memory, so a paused run still counts against the memory budget. Only its slot and its cores are lent. Under pressure the OS can compress or swap a stopped job's pages, which is what eases it.
- **An urgent waiter a rate limit stops** pauses nobody: the quota is checked first.
- **Which resources.** `pausable` in the resource's config, and `rerun` for the ones whose jobs may be stopped and run again from the start (above). On by default for test, heavy and playwright. Off for xcode-build (`xcodebuild test` drives a simulator a pause can't stop, and pausing a real build is untested), deploy (a half-done deploy with remote timeouts running is worse than a slow one) and sim (the app runs under the simulator, outside the job's process tree, so pausing the script leaves the app and the booted device going). Off for names dibs doesn't know. A run on several resources pauses only if all of them allow it. Timers inside a paused job keep counting wall time, so a test or Playwright timeout may fire right after it resumes; the stderr notice says why.
- **Windows** has no SIGSTOP, so nothing is ever paused there.

## Pace and the load ceiling

The budgets above are skipped while the machine looks roomy, and nothing stops new work when the load climbs. `dibs pace` picks how hard dibs drives this machine in one word:

```bash
dibs pace quiet     # the fan stays calm and the person at the Mac never feels it
dibs pace normal    # today's budgets, plus a load ceiling at one job per core
dibs pace max       # finish fast: 1.5 busy jobs per core, three quarters of memory
dibs pace off       # back to the numbers in config.json, no ceiling
dibs pace           # what's set now, and what each pace sets on this machine
```

Each pace sets six knobs from this machine's cores and memory. On a 10-core 16 GB Mac:

| | quiet | normal | max |
|---|---|---|---|
| `cores` in use | 4 (40%) | 6 (60%) | 15 (150%) |
| memory `budget` | 6.5G (40%) | 8G (50%) | 12G (75%) |
| `maxLoad` | 5 (half the cores) | 10 (one per core) | 15 (1.5 per core) |
| `coolLoad` (dibs throttle) | 5 | 8 | 12 |
| budgets skipped when roomy | never | load under 0.6 per core, 35% memory free, memory pressure normal, swap not growing past `maxSwap`, budget not already used up | never |
| `overlap` | off | fit | squeeze |

- **The ceiling.** While the 1-minute load average is above `maxLoad`, new `normal`, `low` and `idle` work waits; `dibs why` and the board say so. `urgent` and `high` work still starts, and so does work that already holds a lease (see nesting), and passes the waiters the ceiling holds back. Work already running is never stopped. Nothing waits on the ceiling forever: a job it alone has held for 20 minutes starts anyway at background priority, on the efficiency cores on Apple silicon, which barely warms the fan the ceiling protects. Jobs started that way share 40% of the cores between them, and one that asks for more still goes when it's alone. Memory, swap and disk limits still hold them. The wait says `held by load since 14:02, starts by 14:22 at the latest`, and that a job a person is waiting on now can go with `-p high -m "why"`, or to another machine with `--on <machine>`. Its agent hears once, through the hook, when it starts this way. On a coordinator with an on-demand machine (docs/machines.md), a job whose turn in line here is further off than 90 seconds (waking and sending) plus its usual run time goes there at once, and a job the machine has held for 2 minutes (the ceiling, the budgets, memory, swap, or a job ahead reserving memory) goes there instead, when it can run there: not when a resource it needs is macOS-only, its command names a macOS tool (`xcrun`, `swift`, `osascript` and the like) or a path of this machine (`/Users/...`, `~/...`), the script it runs imports Apple frameworks (Vision, Quartz, AppKit), its project's `.dibs.json` keeps it here (`stayOn`), or its folder is your home folder or outside git. Its `dibs run` says where it went, and the job runs there as if sent with `--on`.
- **Bursts.** The load average trails the real load by about a minute: a job started t seconds ago shows in it as only 1 - e^(-t/60s) of its cores. dibs adds the missing part of every recent start to the reading, so ten waiters can't all start under one reading taken before any of them did.
- **Your own numbers win.** A knob set in `~/.dibs/config.json` to anything but its stock value overrides what the pace says. A file dibs wrote holds every stock value, so those don't count as choices. `maxLoad` works on its own too, without a pace.
- **No pace, no change.** Without `pace` or `maxLoad` in the config, dibs behaves exactly as before. The board's first line names the pace when there is one.

## Running side by side

For most resources the slot count stands in for "the machine can take this many". When a resource is full but its jobs leave real room, `overlap` lets one more start on top:

- **`fit`.** A job starts on a full resource when its size fits what's really free right now: memory stays above `minFreeMem`, and the load stays under `maxLoad` (one per core without a ceiling). Its size is the most its command used in recent measured runs (see "Measuring what jobs use"), else the `--mem` it asked for. A command dibs has never measured, run without `--mem`, has an unknown cost and waits for a slot.
- **`squeeze`.** Also: a job that usually takes less than `squeezeUnder` (60s, from its run history, never `--est`) starts if its memory fits, even if its cores take the load past `maxLoad`. You accept that load hit by choosing it. Not once the load is already past it.
- **`off`.** One job per slot, as before.
- **Who decides.** `dibs pace` sets it: `quiet` off, `normal` fit, `max` squeeze, and off without a pace. `"overlap"` in `~/.dibs/config.json` wins over the pace. Switching the pace is the person's call: an agent's `dibs pace <word>` is refused.
- **Never on.** Resources that are one at a time: `exclusive: true` in their config (`sim` and `deploy` by default), names dibs doesn't know (often someone's lock; set `"unknown": { "exclusive": false }` to change that), the `sim-own` pool, resources with an `onRelease` reset, file leases and quotas. Nor holds: a hold keeps the resource to itself.
- **Bursts.** The free-memory reading lags a start by up to half a minute while a job loads, and the load average by a minute. Jobs started in the last 30 seconds count at their size, less what dibs has already measured them using, and recent starts count against the load as they do for the ceiling.
- **Fair.** A job on top never takes a slot. When a slot frees, the next waiter in the queue gets it as usual, so a big job waiting for a slot isn't passed for good by small ones running on top. A waiter ahead that fits on top too goes first. The budgets, disk, swap, memory and load rules still apply, and the memory budget always does: a job on top never gets the roomy exception. Nobody is paused or slowed to make room.
- **Under memory pressure** jobs on top pause first, newest first, and resume last (on resources that allow pausing; `xcode-build` doesn't). They're never killed.
- **What you see.** `dibs run` says `the test queue is full, so this runs alongside web-app: it needs about 0.5 GB of memory, and there's room.` The plain board says `api is running alongside web-app, since the machine had room` or `squeezed in next to web-app, since it usually takes under a minute`, and `dibs --detail` marks the row `[running alongside web-app]` or `[squeezed in (usually takes under a minute)]`. `dibs why` explains a refusal: `Can't run alongside: it usually needs 6.0 GB of memory and 3.0 GB is free.` A command dibs has never measured needs `--mem` the first time to run alongside.

## Putting a resource back

A resource can name a command that runs after each lease on it ends, so the next agent finds it the way you want it. For the shared simulator, a reset to the default text size, light mode and a clean status bar:

```json
"resources": {
  "sim": { "onRelease": "xcrun simctl ui booted content_size large; xcrun simctl ui booted appearance light; xcrun simctl ui booted increase_contrast disabled; xcrun simctl status_bar booted clear" }
}
```

- **When.** Once per lease end, however it ends: the command exits, crashes, dibs is killed with `-9` (the next dibs call notices), a hold is released or runs out. A run under your own session's hold isn't the end of your turn: the hold's end is.
- **The next user waits for it.** Until the reset finishes, the next lease on that resource waits (`Waiting for the simulator to be reset after onboarding's turn`), so it can't race them. It gets `onReleaseTimeout` (default `30s`) and is then killed with everything it started.
- **It never fails anyone.** It runs outside the state lock in its own process, with `$DIBS_RESOURCE` and `$DIBS_RELEASED_BY` set, from `~/.dibs`. A failure or timeout is logged to `~/.dibs/onrelease.log` with the end of its output; the job's exit code is its own.
- Use `;` between steps rather than `&&`, so one failing step (no simulator booted) doesn't skip the rest.
- `booted` means the one booted simulator. While `sim-own` devices are booted too, put the shared simulator's udid in its place (`xcrun simctl list devices booted`).

## Throttling

`dibs throttle --watch` runs a watcher. When the 1-minute load is over `coolLoad` (8, or what `dibs pace` sets), build and test processes that keep a core hot outside any lease are moved to background priority (the efficiency cores on Apple silicon, nice 10 on Linux). Nothing is killed. The same watcher pauses idle and low runs under heavy memory pressure, and runs below high when swap fills the disk (see above). Moves are logged to `~/.dibs/cool.log`. `dibs throttle` does one pass.
